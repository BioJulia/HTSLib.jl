HTSLib.jl

Julia bindings to htslib, the C library behind bgzip, tabix and samtools, loaded from htslib_jll.

HTSLib.jl compresses files with BGZF, builds and loads tabix indexes, and reads records by region or from start to end, as the bgzip and tabix command-line tools do. It reads SAM, BAM and CRAM files, from start to end and by region, as samtools does. Its main use is as a reference implementation in-process, to validate and benchmark Julia packages such as Tabix.jl, BED.jl and XAM.jl against htslib without starting a process for each call.

BGZF and tabix

using HTSLib

compressed = bgzip("features.bed")                 # "features.bed.gz", keeping "features.bed"
index = tabix_index(compressed; preset = :bed)     # "features.bed.gz.tbi"
tabix_index(compressed; csi = true)                # "features.bed.gz.csi"

TabixFile(compressed) do file
    sequence_names(file)                                 # ["chr1", "chr2", …]
    query(file, "chr1:1001-2000")                  # Vector{TabixRecord}, as `tabix features.bed.gz chr1:1001-2000`
    query(file, "chr1", 1001, 2000)                # the same region, 1-based and inclusive
    records(file)                                  # every record, from start to end
end

A TabixRecord has the sequence name, the interval, and the line of a record; HTSLib.sequence_name(record) gives the sequence name, after the tabix specification's "Column for the sequence name". As in htslib, intervals are 0-based and half-open, whatever the positions of the file: start is the position of the first base, and stop the position after the last.

query and records copy each record. To read without allocating, each_overlap and each_record yield a RecordView of each record, which is only valid until the next iteration:

TabixFile(compressed) do file
    total = 0
    for record in each_overlap(file, "chr1:1001-2000")
        total += record.stop - record.start        # String(record) copies the line
    end
    total
end

tabix_index also takes the columns and header settings of tabix -s, -b, -e, -0, -c and -S; see its docstring.

SAM, BAM and CRAM

using HTSLib

AlignmentFile("reads.bam") do file
    HTSLib.format(file)                            # :bam
    sequence_names(file), sequence_lengths(file)               # the reference sequences of the header
    String(file.header)                            # the header text
    records(file)                                  # every record, as `samtools view reads.bam`
    for record in query(file, "chr1:1001-2000")    # as `samtools view reads.bam chr1:1001-2000`
        string(record)                             # the SAM line, as samtools prints it
        HTSLib.pos(record), HTSLib.end_position(record)
    end
end

HTSLib.jl only reads alignment files, to report what htslib finds in them; XAM.jl implements the formats in Julia. Test files can be converted from SAM and indexed with htslib through HTSLib.Bindings, as samtools does, which the tests of HTSLib.jl show.

A CRAM file needs its FASTA reference, AlignmentFile("reads.cram"; reference = "genome.fa"), or htslib looks it up as samtools does, which may download it. As samtools does, htslib adds MD and NM tags computed from the reference to the records of a CRAM file.

Records are AlignmentRecords, which own their data, or AlignmentViews, which each_record and each_overlap yield without allocating and which are only valid until the next iteration. string(record) gives the SAM line of a record, with every field. The accessors give what htslib makes of a record's name and position. They take the names of the SAM specification's fields, with aliases where the specification names a field otherwise, and are public but not exported, since their names are common:

With GenomicFeatures loaded, alignments and Tabix records have its interval interface: group_name is rname of an alignment and sequence_name of a Tabix record, and left_position and right_position are 1-based and inclusive.

Low-level bindings

The low-level bindings, a ccall of each C function used and the C structs, are in HTSLib.Bindings. Each function there carries the C declaration it binds in a comment, and structs used only through pointers, such as BGZF, hts_idx_t and sam_hdr_t, are named opaque types.

The bindings cover more of htslib than HTSLib.jl itself uses, such as writing alignments and building their indexes, for packages that need them.

Most of the bindings are generated with Clang.jl from the headers of htslib_jll, as gen/selection.jl selects them, and the generator checks the structs written by hand against htslib; gen/README.md describes how to add a function and regenerate them.

HTSLib.version() gives the version of the loaded htslib, and HTSLib.is_available() whether htslib_jll provides it for this platform.
